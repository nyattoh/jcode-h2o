# 第2〜3段階の補強記録

Kotaの追加指示（2026-11-10 21:20 JST）を受け、第4段階へ進まず、第2〜3段階の反例試験と設計文書を補強する。
時間の目安は指示中の22:20 JSTと解釈する。禁止事項と共通設定・scriptsを変更しない条件は維持する。

## 仮定

- 監視journalの欠損は新しいrun開始の根拠ではない。初期契約やcheckpointを欠く場合、予算を初期化して制御を再発行せず、照合が必要として止める。
- プロセス中断と電源断は別の障害として扱う。今回の追加試験も非機密の合成データとローカル模擬制御だけを用いる。
- 原文・checkpoint・制御結果を消去して試験を通す復旧は実装しない。
- ルーター、effort調整、バックグラウンド実行の設計整理は行うが、それらの新機能や第4段階の受付・通信は実装しない。
- 同じrunの同じcall IDは同じ観測を指すものとする。内容が異なる場合は単なる重複として捨てず、相関が不明としてエラーを返す。

## journalの不完全な履歴

追加した反例では、checkpointと応答記録が残る一方で `spec` が失われると、従来コードは新しい契約を書いて再開していた。
また、末尾checkpointだけを失い応答記録が残る場合、その応答を見落として同じsequenceを再利用できた。

- RED：`orphan_receipts_and_missing_contracts_are_not_treated_as_a_fresh_run` が `lost spec must require reconciliation` で失敗（1件失敗、exit 1）。
- 修正：再開前にevent/receiptの名前と対応を調べ、checkpointなしの応答記録、sequenceゼロ、不正な名前、履歴に対する初期契約の欠損を拒否する。
- GREEN：監視契約12件成功、失敗0、exit 0。

これは偶発的な欠損の追加検出であり、改ざん耐性・完全な破損検出の保証ではない。契約・末尾checkpoint・応答記録をまとめて失った場合など、検出できない消失も残る。

## 監視プロセスの強制終了

`monitor_process.rs`は実際のテスト子プロセスを起動し、制御そのものはローカルの合成marker書込みで代用する。

- 制御直前と、合成marker書込み後・応答保存前で子プロセスをkill。新しい子プロセスで2回読み直しても制御を再送せず、照合待ちとなる。
- 応答保存後にkill。別の子プロセスで消費済み予算から上限停止し、さらに別の子プロセスでも停止が保持される。
- 同じjournalを開いた2つの実プロセスを同時に進め、checkpoint予約成功1・衝突1、合成marker1件だけを確認。
- 対象3件が成功（exit 0）。ignored 1件は親から明示起動する子プロセスfixture。

これは実SDK要求の効果や実workerの行動を証明するものではなく、永続化と制御の順序に関する証拠である。

## 状態空間と公開APIの競合試験

枝制御では、9 checkpointの全19,683列を予算0〜3で確認した。各prefixの逸脱回数に基づく閉じた形の期待値と比較し、回復で予算が補充されないことを確認する。
別の試験では、2枝に対する7 checkpointの全279,936通りの割込み順を調べ、片方の履歴が他方の予算や停止へ影響しないことを確認した。対象2件は成功（exit 0）。

公開APIの長時間試験は、3 writerと1 readerの実プロセスを毎回起動し、入力byte列・サイズ・終了タイミング・保存先を変える。
OSの一時ディレクトリとworkspaceのtarget配下を交互に用いる。readerは未公開または完全な候補のbyte列だけを読めること、公開後に値が変わらないこと、commit応答が複数にならないことを確認する。
最大同時子プロセス数は4。通常の試験からは除外し、明示的に `--ignored` で実行する。プロセスfixtureも同じ除外方法を使うため、通常試験のignored数には長時間試験自体も含まれる。

最初の長時間実行のseed式は終了対象がwriter 0に固定される性質を持つ。その実行はwriter 0中断のstressとして記録し、writer 1/2の中断の証拠としない。
この実行の終了結果は後述の「長時間実行の確定結果」に記す。

終了対象の選択はcase数のmoduloで0/1/2を巡回するように補強した。killを要求した回数と、対象プロセスの非正常終了を観測した回数も分けて記録する。
その追加実行はrelease構成で180.13秒、978ケース、readerの確認149,388回、失敗0・exit 0。
kill要求は `[326, 326, 326]`、非正常終了の観測は `[325, 326, 326]`。1件はkillより先に正常終了しており、中断成功として数えていない。
作成を試みたpayloadの論理byte数合計は132,178,866。これはOSの物理I/O量ではない。

## Windowsの予約名

[Microsoftの命名仕様](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)で、標準の予約デバイス名と通常のファイル名を区別する必要を確認した。
従来のASCII英数字・ハイフン・下線だけの検査では `CON` 等もpath変換を通っていた。

- RED：privateなpath検査だけを呼び、予約名が受理されて1件失敗（exit 1）。実デバイスを開く試験はしていない。
- 修正：Windows上ではCON/PRN/AUX/NUL、COM1〜9、LPT1〜9を大文字小文字によらず、file API呼出し前にInvalidInputで拒否する。
- 追加試験：全操作での拒否、似た通常ID（CONSOLE、COM10等）の保存・復元を確認した。
- GREEN：SDK無効の全24件が成功、失敗0、exit 0。

互換性に関する仮定として、この制限はWindowsだけに適用する。他OSでの既存の名前を一律に拒否する変更は加えない。
大文字小文字の扱いを異なるFS間で統一するID仕様、最大長、攻撃者が変更できる保存先の防御は、この修正で保証していない。
